# The Cortes expedition.
#
# WHY THIS EXISTS: in a 12-hour unsteered observer run the AI never took a
# single Mesoamerican location. Nothing in the submod is eligible to fire in a
# region no Old World power has reached, so the whole collapse model sat idle
# over the one region it was built for. EU5's Conquistador mechanic would
# normally cover this; M&T has it disabled.
#
# This forces the historical foothold - Veracruz, 1519, launched from the
# Caribbean - and lets the existing machinery take it from there. It is
# deliberately the SMALLEST possible intervention: one location, once. Nothing
# here conquers Mexico. It gives the beachhead and leaves the rest to the AI,
# the diseases and the region-contact sweep.
#
# SPONSOR: whoever owns Sevilla, not a hardcoded Spain. Historically the same
# thing - the Indies trade was run from Seville under the Casa de
# Contratacion, and Cortes sailed on Castilian authority - but it degrades
# into alternate history gracefully. If Morocco retakes Andalusia before the
# expedition launches, Morocco gets Veracruz. It also dodges the question of
# whether Spain exists as a tag yet at this date.
#
# Player-agnostic either way: it fires the same whoever the human is playing,
# including observer mode.
#
# ============================ STATUS ============================
# CONFIRMED by probe:
#   location:sevilla         valid, and `owner` resolves off it
#   every_owned_location     valid in country scope (reported 244)
#   location:xamapan         valid  - this is Veracruz
#   area:tochtepec_area      valid
#   region:mesoamerica_region valid (control)
#   option = { }             event choices are options
#   change_location_owner    the ownership-transfer effect
#
# RULED OUT by probe:
#   province:                NOT an addressable scope type, despite
#                            cuetlaxtlan_province being a real province key
#   outcome = { }            outcome is a scalar audio enum, not a block
#   set_owner, set_location_owner, change_owner, set_owner_and_controller,
#   transfer_location, cede_location, set_country_owner, add_owned_location,
#   set_controller, become_owned_by        all "Unknown effect"
#
#   outcome = neutral        EAudioEventOutcome takes positive, negative or
#                            neutral; good, bad, none and default are not
#
#   change_location_owner    CONFIRMED at runtime - Xamapan flipped owner
#
# RULED OUT:
#   every firing effect except trigger_event_silently: trigger_event,
#   fire_event, show_event, send_event, country_event,
#   trigger_event_with_popup, trigger_event_visible, trigger_event_shown
#
#   cuetlaxtlan_province     composition read from the game files:
#                            cuetlaxtlan xamapan nopiloa teutila puctlan
#                            otatitlan - all granted individually
#
# STILL OPEN:
#   whether trigger_event_silently suppresses the POPUP or only the
#   notification. The hook is live either way - if it does suppress, the
#   engine resolves on ai_chance (100:0 in favour) and the player loses the
#   veto but not the expedition. Fire `event nwp.20` to find out.
# ================================================================


# --------------------------------------------------------------------
# nwp.23 - DEBUG. Resolve the sponsor and report its New World holdings.
# Console: event nwp.23
#
# Tests tokens 2 and 3, and the real trigger condition, in one command.
# every_owned_location is already proven - nwp.1 uses it successfully.
# --------------------------------------------------------------------
nwp.23 = {
	type = country_event
	title = hidden_event.t
	hidden = yes
	orphan = yes

	immediate = {
		location:sevilla ?= {
			owner ?= {
				save_scope_as = cortes_sponsor
				# MEASURED 1337: this resolved, and reported
				# new_world_locations=0 even with a Castilian colony in Cuba
				# on the map - and in the same log the Situation's can_start
				# fired, which proves SOME Old World power owns a populated
				# American location. So either Sevilla's owner is not the
				# country holding Cuba, or the colony belongs to a subject.
				#
				# total_locations separates those: a Castile-sized number
				# means the owner is right and the American filter is wrong;
				# a handful means Sevilla belongs to someone unexpected.
				set_local_variable = {
					name = nwp_all
					value = { every_owned_location = { add = 1 } }
				}
				set_local_variable = {
					name = nwp_nw
					value = {
						every_owned_location = {
							limit = { continent = continent:america }
							add = 1
						}
					}
				}
				error_log = "::NWPCORTES::[GetCurrentYear]:Sevilla owner resolved:total_locations=[SCOPE.GetLocalVariable('nwp_all').GetValue]:new_world_locations=[SCOPE.GetLocalVariable('nwp_nw').GetValue]"
				remove_local_variable = nwp_all
				remove_local_variable = nwp_nw
			}
		}
	}
}


# --------------------------------------------------------------------
# nwp.24 - DEBUG. Which of these are valid SCOPE TYPES?
# Console: event nwp.24
#
# The in-game debug panel settled the keys outright:
#
#   Location Tag   xamapan
#   Province       cuetlaxtlan_province (3544)
#   Area           tochtepec_area (608)
#   Region         mesoamerica_region (61)
#
# So cuetlaxtlan_province is a real province key after all. What remains
# unknown is whether `province:` and `area:` are addressable scope types the
# way `region:` demonstrably is - the submod already uses
# region:mesoamerica_region every month without complaint.
#
# Grants nothing.
# --------------------------------------------------------------------
nwp.24 = {
	type = country_event
	title = hidden_event.t
	hidden = yes
	orphan = yes

	immediate = {
		location:xamapan ?= {
			error_log = "::NWPKEY::HIT location:xamapan"
		}
		province:cuetlaxtlan_province ?= {
			error_log = "::NWPKEY::HIT province:cuetlaxtlan_province"
		}
		area:tochtepec_area ?= {
			error_log = "::NWPKEY::HIT area:tochtepec_area"
		}
		region:mesoamerica_region ?= {
			error_log = "::NWPKEY::HIT region:mesoamerica_region (control - this one must hit)"
		}
		error_log = "::NWPKEY::probe complete"
	}
}


# --------------------------------------------------------------------
# nwp.27 - DEBUG. Does change_location_owner actually work at runtime?
# Console: event nwp.27
#
# Passing the load check only proves the effect EXISTS. This proves it does
# the thing. Hidden with no options, so it needs no outcome enum and is
# testable while that question is still open - otherwise the grant could not
# be tested until the enum is known, and both would need another launch.
#
# Grants Xamapan to whoever owns Sevilla. Run it on a throwaway save.
# --------------------------------------------------------------------
nwp.27 = {
	type = country_event
	title = hidden_event.t
	hidden = yes
	orphan = yes

	immediate = {
		location:sevilla ?= {
			owner ?= { save_scope_as = cortes_sponsor }
		}
		# cuetlaxtlan_province, from the game files:
		#   cuetlaxtlan xamapan nopiloa teutila puctlan otatitlan
		#
		# Granted one location at a time rather than through the province.
		# `province:` is not an addressable scope type, and while `province`
		# might work as a transition off a location, `location:` is already
		# proven and this needs no further probing. The cost is that the list
		# is pinned to M&T's current province composition - if that changes,
		# this list goes stale silently. Each is ?= guarded, so a renamed or
		# removed location drops out rather than breaking the grant.
		location:cuetlaxtlan ?= { change_location_owner = scope:cortes_sponsor }
		location:xamapan ?= { change_location_owner = scope:cortes_sponsor }
		location:nopiloa ?= { change_location_owner = scope:cortes_sponsor }
		location:teutila ?= { change_location_owner = scope:cortes_sponsor }
		location:puctlan ?= { change_location_owner = scope:cortes_sponsor }
		location:otatitlan ?= { change_location_owner = scope:cortes_sponsor }
		error_log = "::NWPCORTES::[GetCurrentYear]:DEBUG province grant executed"
	}
}


# --------------------------------------------------------------------
# nwp.20 - the Cortes expedition. VISIBLE, with a choice.
#
# Hooked into the Situation's on_monthly. Still orphan = yes so it can also
# be fired from the console for presentation checks.
#
# Two options, affirmative listed first so it is the player's default. The AI
# takes it at 100:0, so an observer run or an AI Castile always follows
# history while a human player keeps the veto.
#
# Declining sets the same done flag, so it asks once and then leaves you
# alone. Be aware that declining means nothing gives Mesoamerica a European
# foothold - which is precisely the untouched-Mexico outcome the 12-hour
# observer run produced, so the submod will have little to do there.
#
# If you would rather it keep asking every generation instead of once, drop
# the set_global_variable from the decline option and add a date check to the
# hook's limit.
#
# ADDITIONAL UNVERIFIED TOKENS: ai_chance, and the two scope branches below.
# Both grants are wrapped in ?= so whichever key form is wrong no-ops rather
# than firing. That handles a bad KEY. If `province:` or `location:` is not a
# valid scope TYPE at all it will be a load-time parse error instead, which
# shows up in error.log the moment the mod loads - check there first.
# --------------------------------------------------------------------
nwp.20 = {
	type = country_event
	title = nwp.20.t
	desc = nwp.20.d
	orphan = yes

	# MEASURED: EAudioEventOutcome accepts positive, negative and neutral.
	# good, bad, none and default were all rejected. This is an event-level
	# audio cue, not a per-option one - the engine reported it missing against
	# the event, not the options. neutral because this is a decision prompt
	# rather than good or bad news arriving.
	outcome = neutral

	# Events use `option` blocks. The first attempt read the error "missing an
	# outcome" as meaning EU5 renames options to outcomes; it does not, and
	# switching the blocks over produced "Event #nwp.20 has no options" plus a
	# parse cascade. Both are needed, and they are different things.
	#
	# Affirmative first so it is the player's default.
	option = {
		name = nwp.20.a
		ai_chance = { factor = 100 }

		# MEASURED: province: is NOT an addressable scope type. nwp.24 hit
		# location:xamapan, area:tochtepec_area and region:mesoamerica_region
		# but not province:cuetlaxtlan_province, so the grant targets the
		# location directly.
		#
		# MEASURED: change_location_owner is the ownership effect. Nine other
		# candidates were reported "Unknown effect" at load; this one was not.
		# cuetlaxtlan_province, from the game files:
		#   cuetlaxtlan xamapan nopiloa teutila puctlan otatitlan
		#
		# Granted one location at a time rather than through the province.
		# `province:` is not an addressable scope type, and while `province`
		# might work as a transition off a location, `location:` is already
		# proven and this needs no further probing. The cost is that the list
		# is pinned to M&T's current province composition - if that changes,
		# this list goes stale silently. Each is ?= guarded, so a renamed or
		# removed location drops out rather than breaking the grant.
		location:cuetlaxtlan ?= { change_location_owner = root }
		location:xamapan ?= { change_location_owner = root }
		location:nopiloa ?= { change_location_owner = root }
		location:teutila ?= { change_location_owner = root }
		location:puctlan ?= { change_location_owner = root }
		location:otatitlan ?= { change_location_owner = root }
		error_log = "::NWPCORTES::[GetCurrentYear]:expedition accepted, Cuetlaxtlan province granted"
	}

	option = {
		name = nwp.20.b
		ai_chance = { factor = 0 }

		error_log = "::NWPCORTES::[GetCurrentYear]:expedition declined"
	}
}


# --------------------------------------------------------------------
# The hook, now live in the Situation's on_monthly:
#
#	if = {
#		limit = {
#			NOT = { has_variable = nwp_cortes_done }
#			current_date > 1510.1.1
#		}
#		set_variable = nwp_cortes_done
#		location:sevilla ?= { owner ?= { trigger_event = nwp.20 } }
#	}
#
# Situation-scope set_variable, not a global variable: the situation form is
# proven and the global form is not, and a situation is a singleton anyway.
# The scope is nested rather than chained as location:sevilla.owner, and the
# call is bare trigger_event rather than a { id = } block, both to stay on
# constructs this codebase has already executed successfully.
#
# NOTE THE MISSING CONDITION. The plan was to require Sevilla's owner to hold
# an American location. That does not work, and the probe shows why:
#
#	total_locations=244 : new_world_locations=0
#
# 244 locations is a major Iberian power, so the sponsor resolves correctly -
# but it holds zero American locations in a game where the Situation had
# already started, which proves some Old World power owns a populated
# American location. The colony belongs to a SUBJECT, not the parent.
#
# Which means the original instinct - "when Spain has a subject in the New
# World" - was right, and requiring direct ownership would have produced an
# event that silently never fires. Exactly the failure this submod keeps
# hitting.
#
# Rather than guess a subject-iterator token, the condition is dropped
# entirely. This hook lives inside the Situation's on_monthly, and the
# Situation cannot be running unless an Old World power already owns a
# populated American location - its can_start says so. So "Europe has
# arrived" is already guaranteed by the fact that this code is executing.
#
# Tradeoff: if Portugal colonises and Castile does not, Castile still gets
# Veracruz. Slightly odd, and preferable to never firing. A subject-aware
# version can tighten it later once the iterator token is known.
#
# trigger_event, NOT trigger_event_silently - the silent form would suppress
# the popup and take the player's choice away.
#
# The date gate keeps it near 1519. The global variable is set BEFORE firing
# so it cannot re-ask while the popup is open. The sponsor is resolved at
# firing time, so a conquest of Andalusia in 1515 redirects the expedition;
# one in 1530 does not.
# --------------------------------------------------------------------
